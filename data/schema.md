# Synthetic batch schema

`synthetic_batch.json` contains **60 synthetic** (clearly not real) failed/degraded
payment records, generated by `generate_batch.py` with a fixed seed (`7`) so
results are reproducible run-to-run for the metrics report.

| Field | Type | Description |
|---|---|---|
| `payment_id` | string | Synthetic Razorpay-style payment id |
| `customer_id` | string | Synthetic customer id |
| `customer_name` | string | Synthetic name (Faker-style, not real people) |
| `customer_phone` | string | Masked phone, e.g. `72xxxxx68` |
| `amount_paise` | int | Amount at risk, in paise (Razorpay convention: ₹1 = 100 paise) |
| `currency` | string | Always `INR` |
| `failure_code` | string | Raw gateway/bank failure code (see below) |
| `failure_message` | string | Freeform failure text — this is what the LLM classifier reasons over |
| `subscription_id` | string\|null | Present if this is a recurring/subscription charge |
| `attempt_count` | int | How many recovery attempts have already happened before this run |
| `created_at` | ISO datetime | When the failure occurred |
| `is_recurring` | bool | Whether this is a subscription/mandate-based payment |

## `failure_code` values and their mapped root cause

| failure_code | Root cause |
|---|---|
| `INSUFFICIENT_FUNDS` | `insufficient_funds` |
| `CARD_EXPIRED` | `card_expired` |
| `ISSUER_DECLINED`, `ISSUER_UNAVAILABLE` | `bank_decline_soft` |
| `MANDATE_REVOKED` | `mandate_revoked` |
| `SUSPECTED_FRAUD` | `fraud_hold` |
| `GATEWAY_TIMEOUT` | `technical_timeout` |

Any code not in this table is classified `unknown` and hard-routed to human
escalation (see `agent/rules_config.yaml`).

## Regenerating / scaling the batch

```bash
python -m data.generate_batch --count 100 --seed 7 --out data/synthetic_batch.json
```
